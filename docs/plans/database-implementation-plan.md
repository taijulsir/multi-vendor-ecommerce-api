This document translates the 11 approved domain architecture documents in
`docs/database/` into one concrete, ordered implementation plan for the
`prisma/schema/*.prisma` files, migrations, and seed data. It does **not**
modify any code. It exists so that the actual schema-writing work can proceed
mechanically from a single reviewed reference instead of being re-derived
from eleven separate documents.

Every decision below is either:

- **Approved** — taken directly from a `docs/database/*.md` file, or
- **Implementation Decision** — a concrete choice this plan makes to fill a
  gap the architecture docs intentionally left open (e.g. exact `Decimal`
  precision, table naming, migration slicing). These are called out

# Part 1 — Global Conventions (Implementation Decisions)

These apply uniformly across all 35 models unless a domain section says
otherwise. Stating them once here avoids repeating `@id @default(uuid(7))
@db.Uuid` boilerplate 35 times below.

## 1.1 Primary Keys

Every table uses a database-native UUID primary key, generated by Prisma as
**UUID v7** (client-side `uuid(7)`), stored as a real Postgres `uuid`
column:

```prisma
id String @id @default(uuid(7)) @db.Uuid
```

All foreign key columns are typed `String @db.Uuid` to match.

> **Finalized: UUID v7.** The architecture docs only say "UUID / Generated"
> without pinning a version, so there is no architectural conflict either
> way. UUID v7 is time-ordered (monotonic), which gives materially better
> B-tree insert locality than random v4 on every high-insert table in this
> schema (`OrderItem`, `WalletTransaction`, `InventoryTransaction`,
> `AuditLog`, `Notification`, `OrderStatusHistory`,
> `VendorOrderStatusHistory`, `CouponRedemption`) and costs nothing —
> `uuid(7)` is a first-class value for Prisma's `uuid()` function (accepts
> `4` or `7`, default `4`) since **Prisma ORM 5.18.0** (Aug 2024); no
> preview feature flag is required. This repo is already on
> `prisma`/`@prisma/client` `^7.9.1`, well past that baseline, so it's used
> unconditionally: **`@default(uuid(7))` on every model, no exceptions.**
> Sortable IDs are also a minor operational win for this project — e.g.
> `AuditLog`/`WalletTransaction` rows naturally sort by creation order even
> without touching `createdAt`.

## 1.2 Timestamps

- Mutable business entities: `createdAt DateTime @default(now())` +
  `updatedAt DateTime @updatedAt`.
- Immutable ledger/history rows (transactions, status history, audit,
  redemptions, webhook events): `createdAt` only — no `updatedAt`, matching
  each domain doc's explicit "immutable" requirement.
- Soft-deletable entities additionally get `deletedAt DateTime?`.

## 1.3 Soft Delete

Per-entity `deletedAt DateTime?` is used on: `User`, `Vendor`, `Shop`,
`Category`, `Product`, `ProductVariant`, `ProductImage`. These are the
entities the source docs explicitly mark as soft-deletable historical
references (see each doc's "Soft Delete Strategy" section).

Everything else is either:
- a pure historical/immutable record that is never deleted (`MasterOrder`,
  `VendorOrder`, `OrderItem`, `Payment`, `Refund`, `WalletTransaction`,
  `AuditLog`, status-history tables, etc.), or
- a disposable operational row with no soft-delete need (`CartItem`,
  `UserRole`, `RolePermission`), or
- a lifecycle entity controlled entirely by its `status` enum instead of
  `deletedAt` (`Promotion`, `Coupon`, `Wallet`, `Review`, `Notification`).

**Application-layer rule (not enforced by the DB):** every read query on a
soft-deletable model must filter `deletedAt: null` unless explicitly querying
history/admin views. This will be implemented as a Prisma Client extension
or a repository-level default filter during the service-layer phase — out of
scope for this plan, noted here so it isn't forgotten.

## 1.4 Money

All monetary columns use exact `Decimal`:

```prisma
amount Decimal @db.Decimal(14, 2)
```

**Implementation Decision:** `Decimal(14, 2)` platform-wide (12 integer
digits + 2 decimal places → supports up to 999,999,999,999.99), applied
consistently to every money field across every domain (`price`,
`compareAtPrice`, `costPrice`, all `Order`/`Payment`/`Refund`/`Wallet`
amounts, `Promotion` discount values). The one exception is `Commission.rate`,
which is a percentage, not a currency amount: `Decimal @db.Decimal(5, 2)`
(0.00–999.99, with 0–100 enforced at the application layer).

Currency is always `String @db.Char(3)` (ISO-4217-style code, e.g. `BDT`,
`USD`), stored alongside every monetary value per the architecture docs'
explicit "currency travels with the amount" rule. No `Currency` enum is
used — the docs treat this as an open string precisely so new currencies
don't require a migration.

JavaScript floating-point is never used for money; this is a hard rule
repeated in every source document and carries through to the service layer
(out of scope here, but the schema must not make Decimal optional where
money is involved).

## 1.5 JSON Fields

`Json` type, `@default("{}")` where the doc specifies a `{}` default,
otherwise required. Used for: `ProductVariant.attributes`,
`CartItem.selectedAttributes`, `OrderItem.attributes`,
`MasterOrder.shippingAddressSnapshot` / `billingAddressSnapshot`,
`PaymentAttempt.metadata`, `PaymentWebhookEvent.payload`,
`WalletTransaction.metadata`, `Notification.data`, `AuditLog.metadata`.

These are intentionally **not** normalized further — every source doc
explains why (flexible per-category attributes, provider-specific webhook
payloads, generic audit context) and explicitly defers normalization to a
future domain if ever needed.

## 1.6 Enums

Every enum from the architecture docs becomes a native Prisma `enum` (backed
by a Postgres `ENUM` type), never a plain string with app-level validation.
Full catalog in Part 4.

`Role` and `Permission`, however, are **not** enums — per
`identity-access.md` §"Why Role Is a Database Table", they are deliberately
regular tables so new roles/permissions can be added without a migration.
This is the one place the docs explicitly reject the enum approach; it's
called out here so it isn't "fixed" by mistake during implementation.

## 1.7 Naming / Mapping

**Implementation Decision:** Prisma models stay `PascalCase` / fields stay
`camelCase` (idiomatic TypeScript), mapped to `snake_case` tables/columns in
Postgres (idiomatic SQL) via `@@map` / `@map`. Example pattern established
once here and then applied mechanically to every model below without
re-annotating every single field:

```prisma
model MasterOrder {
  id          String   @id @default(uuid(7)) @db.Uuid
  orderNumber String   @unique @map("order_number")
  userId      String   @db.Uuid @map("user_id")
  createdAt   DateTime @default(now()) @map("created_at")
  // ...
  @@map("master_orders")
}
```

To keep the entity tables in Part 5 readable, the per-field `@map(...)` is
**omitted** from every snippet (it is mechanical: `camelCase` → `snake_case`
on every field), but `@@map("...")` for the table name is always shown. If
the team prefers to skip DB-level snake_case entirely and let Postgres
columns match Prisma's camelCase directly, this is the single flag to flip
before the first migration — nothing else in this plan depends on it.

## 1.8 Referential Actions (`onDelete` / `onUpdate`)

The architecture docs consistently forbid hard-deleting historical/financial
records and prefer status-based lifecycle changes. This plan translates that
into an explicit `onDelete` policy so it isn't left to Prisma's default per
relation:

| Relation shape | `onDelete` | Reasoning |
|---|---|---|
| Pure join/assignment table → its parents (`UserRole`→User/Role, `RolePermission`→Role/Permission, `PromotionVendor/Product/Category`→Promotion) | `Cascade` | Assignment rows have no independent meaning once either side is gone. |
| Exclusive child collection with no independent lifecycle (`CartItem`→Cart, `ProductImage`→Product/Variant, `OrderStatusHistory`→MasterOrder, `VendorOrderStatusHistory`→VendorOrder) | `Cascade` | These rows exist only to describe their parent; parent deletion (rare, admin-only) should not orphan them. |
| Core business/financial record → its owner (`Product`→Vendor, `ProductVariant`→Product, `Inventory`→ProductVariant, `VendorOrder`→MasterOrder, `OrderItem`→VendorOrder, `Payment`→MasterOrder, `PaymentAttempt`→Payment, `Refund`→Payment, `WalletTransaction`→Wallet, `Commission`→VendorOrder) | `Restrict` | These are historical/financial records. The parent must never be hard-deleted while children exist; soft delete (`deletedAt`/status) is the only supported removal path. Restrict makes an accidental cascading delete a hard DB error instead of silent data loss. |
| Cross-domain reference to a permanent record (`OrderItem`→Product/ProductVariant, `Review`→Product/OrderItem, `CouponRedemption`→MasterOrder/User/Coupon) | `Restrict` | Same reasoning — these are historical snapshots, not live joins that should cascade. |
| Optional/lookup reference where the parent may legitimately outlive the child pointer (`AuditLog.actorUserId`→User, `InventoryTransaction`, `Notification.userId`→User) | `Restrict` (or `SetNull` where the FK is already nullable, e.g. none here — all are required) | Preserves audit/notification history even if we decide to hard-delete a user account in an exceptional GDPR-style flow; that flow would need an explicit anonymization step, not a cascading delete. |

`onUpdate` is left at Prisma's default (`Cascade` for the FK value only,
i.e. if a PK ever changed) everywhere — PKs are immutable UUIDs so this
never actually fires.

## 1.9 Concurrency & Transactions

Per `catalog.md` §47, `wallet-commission.md` §25, and `order.md` §34, the
following operations must run inside explicit Prisma `$transaction` blocks
with row-level locking (`SELECT ... FOR UPDATE` via
`$queryRaw`/`$executeRaw`, since Prisma's high-level API doesn't expose
`FOR UPDATE` directly) — **noted here as a schema-adjacent requirement, not
implemented by this plan**:

- Inventory reservation/release (`Inventory` row lock during checkout).
- Wallet balance mutation (`Wallet` row lock + `WalletTransaction` insert,
  atomic).
- Coupon redemption against `usageLimit` (`Coupon`/`Promotion` row lock +
  `CouponRedemption` insert).
- Payment/Refund state transitions (idempotency check + status update,
  atomic).

No schema change is required to support this beyond the indexes already
planned in Part 5 — this is flagged so the service-layer implementation
phase doesn't have to rediscover it.

## 1.10 Identifier Generation (`orderNumber`, `paymentNumber`, `refundNumber`)

All three docs explicitly forbid `COUNT(*) + 1`. **Implementation Decision:**
use a dedicated Postgres `SEQUENCE` per prefix, created via raw SQL in the
relevant migration (Prisma schema has no native `CREATE SEQUENCE` syntax),
and format the human-readable number at the application layer inside the
same transaction that creates the row:

```sql
CREATE SEQUENCE order_number_seq;
CREATE SEQUENCE payment_number_seq;
CREATE SEQUENCE refund_number_seq;
```

```text
orderNumber   = 'ORD-' || year || '-' || lpad(nextval('order_number_seq')::text, 6, '0')
paymentNumber = 'PAY-' || year || '-' || lpad(nextval('payment_number_seq')::text, 6, '0')
refundNumber  = 'REF-' || year || '-' || lpad(nextval('refund_number_seq')::text, 6, '0')
```

This is collision-safe under concurrency (`nextval` is atomic) and doesn't
require locking the whole table. The sequences are created via a
`migration.sql` edit (Prisma supports raw SQL in migrations) at the same
step the `MasterOrder`/`Payment`/`Refund` models are added.

## 1.11 Partial Unique Index (Active Cart)

`cart.md` §32 requires "one active cart per user," expressed as:

```sql
UNIQUE(userId) WHERE status = 'ACTIVE'
```

**Verified against the installed Prisma version (`prisma`/`@prisma/client`
`^7.9.1`, per `package.json`):** Prisma ORM shipped a `partialIndexes`
preview feature (introduced in the 7.4 line, confirmed still current at
7.9) that adds a `where` argument directly to `@unique`, `@@unique`, and
`@@index`, for PostgreSQL, SQLite, SQL Server, and CockroachDB. This
supersedes the earlier plan of hand-editing generated migration SQL — the
constraint is now declared natively in the schema:

```prisma
generator client {
  provider        = "prisma-client"
  output          = "../src/generated/prisma"
  previewFeatures = ["partialIndexes"]
}
```

```prisma
model Cart {
  // ...fields...

  @@unique([userId], map: "cart_one_active_per_user", where: raw("status = 'ACTIVE'"))
  @@index([userId])
  @@index([status])
  @@map("carts")
}
```

The `where` argument accepts either `raw("<SQL expression>")` (used here,
since the documented/confirmed syntax for comparing against an enum value
is the raw form) or a type-safe object literal for simple equality checks
on non-enum columns. The plain `@@index([userId])` is kept alongside the
partial unique index because it covers lookups across **all** carts
(converted/abandoned/expired history), which the partial index — scoped to
`status = 'ACTIVE'` rows only — cannot serve.

**Implementation Decision (updated from the previous draft):** since this
is a *preview* feature, confirm at implementation time that
`previewFeatures = ["partialIndexes"]` is added to the generator block in
`prisma/schema/schema.prisma` before the Phase 4 (Cart) migration runs, and
that `prisma migrate dev` is able to generate the `WHERE` clause correctly
for the `Cart` table without manual SQL intervention. No manual migration
edit is required for this constraint anymore.

# Part 2 — Domain Dependency Graph & Implementation Order

Each domain is implementable only after every domain it has a hard foreign
key into already exists. This graph is derived from the FK relationships
documented in each `docs/database/*.md`, not just narrative ordering:

```text
Phase 1  Identity & Access        (no dependencies)
Phase 2  Vendor & Shop            → User
Phase 3  Catalog                  → Vendor
Phase 4  Cart                     → User, ProductVariant
Phase 5  Order                    → User, Vendor, Product, ProductVariant
Phase 6  Payment & Refund         → MasterOrder
Phase 7  Wallet & Commission      → Vendor, VendorOrder
Phase 8  Promotion & Coupon       → User, Vendor, Product, Category, MasterOrder
Phase 9  Review & Rating          → User, Product, OrderItem
Phase 10 Notification             → User
Phase 11 Audit & Activity         → User (optional actor FK)
```

Rationale for the specific ordering choices:

- **Cart before Order (4 before 5):** Cart has no FK *into* Order (the
  relationship is conceptual — Order creates its own snapshots per
  `order.md` §53), but Cart does depend on `ProductVariant` (Catalog), and
  placing it before Order matches the real user journey (browse → cart →
  checkout → order) and lets checkout-flow validation logic build
  incrementally.
- **Payment & Refund after Order (6 after 5):** `Payment.masterOrderId` is a
  hard FK to `MasterOrder`.
- **Wallet & Commission after Order (7 after 5):** `Commission.vendorOrderId`
  is a hard FK to `VendorOrder`. Wallet itself only needs `Vendor` (Phase 2)
  but `Commission` needs `VendorOrder`, so the whole domain waits for Phase 5.
- **Promotion & Coupon after Order (8 after 5):** `CouponRedemption`
  has a hard FK to `MasterOrder`, even though `Promotion`/`Coupon`/the
  targeting tables (`PromotionVendor/Product/Category`) only need Vendor,
  Product, and Category (Phases 2–3). The domain is kept together as one
  migration phase rather than split, since `Coupon`→`Promotion` and
  `CouponRedemption`→`Coupon` are tightly coupled within the same doc.
- **Review after Order (9 after 5):** `Review.orderItemId` is a hard FK to
  `OrderItem`.
- **Notification and Audit last (10, 11):** both only need `User`, and both
  are designed to reference every other domain purely through
  `type`/`resourceType` + `data`/`metadata` JSON — no hard FKs into Catalog,
  Order, Payment, Wallet, Promotion, or Review. They are ordered last
  because they are conceptually "observers" of everything else, not because
  the DB requires it; either could technically move earlier without
  breaking anything.

# Part 3 — Prisma Schema File Layout (Implementation Decision)

**Decision:** move from the current single `prisma/schema.prisma` to
Prisma's multi-file schema, one file per domain, mirroring
`docs/database/*.md` 1:1. This keeps each file reviewable against its source
document and keeps the domain boundaries the architecture docs already
established visible in the codebase, instead of one 2000+ line file.

```text
prisma/
├── schema/
│   ├── schema.prisma              # generator + datasource only
│   ├── enums.prisma                # every enum (Part 4)
│   ├── identity-access.prisma      # User, Role, Permission, UserRole, RolePermission
│   ├── vendor-shop.prisma          # Vendor, Shop
│   ├── catalog.prisma              # Category, Product, ProductVariant, ProductImage, Inventory, InventoryTransaction
│   ├── cart.prisma                 # Cart, CartItem
│   ├── order.prisma                # MasterOrder, VendorOrder, OrderItem, OrderStatusHistory, VendorOrderStatusHistory
│   ├── payment-refund.prisma       # Payment, PaymentAttempt, PaymentWebhookEvent, Refund
│   ├── wallet-commission.prisma    # Wallet, WalletTransaction, Commission
│   ├── promotion.prisma            # Promotion, Coupon, PromotionVendor, PromotionProduct, PromotionCategory, CouponRedemption
│   ├── review.prisma               # Review
│   ├── notification.prisma         # Notification
│   └── audit.prisma                # AuditLog
└── migrations/
```

Required companion changes (not made by this plan, listed for the
implementation step):

- `prisma.config.ts`: change `schema: 'prisma/schema.prisma'` to
  `schema: 'prisma/schema'` (directory form).
- `prisma/schema/schema.prisma` (the file) keeps only the `generator` and
  `datasource` blocks; all models/enums move to the new files. Prisma's
  multi-file loader merges every `.prisma` file in the directory into one
  logical schema, so cross-file model references (e.g. `Product` in
  `catalog.prisma` referencing `Vendor` in `vendor-shop.prisma`) work with
  no special syntax.
- The `generator` block in that file must include
  `previewFeatures = ["partialIndexes"]` (§1.11) before the Phase 4 (Cart)
  migration is generated.

**Finalized:** this multi-file layout is confirmed and kept — each file
mirrors its `docs/database/*.md` source 1:1, so a reviewer can diff a
schema file against its source doc directly. Part 6's per-domain migration
sequence (one `prisma migrate dev` per phase) is likewise confirmed and
kept, for the same reviewability reasons plus the natural checkpoints it
gives for the manual sequence-creation steps in §1.10.

# Part 5 — Domain-by-Domain Schema

Each model below is written as it is intended to appear in its
`prisma/schema/*.prisma` file. Field-level `@map` is omitted per §1.7;
`@@map` (table name) is always shown. `onDelete` follows §1.8's policy table.

## Phase 1 — Identity & Access (`identity-access.prisma`)

Source: `docs/database/identity-access.md`. No dependencies — this is the
foundation migration.

```prisma
model User {
  id              String    @id @default(uuid(7)) @db.Uuid
  email           String    @unique
  passwordHash    String
  firstName       String
  lastName        String?
  phone           String?
  avatarUrl       String?
  status          UserStatus @default(ACTIVE)
  emailVerifiedAt DateTime?
  lastLoginAt     DateTime?
  createdAt       DateTime  @default(now())
  updatedAt       DateTime  @updatedAt
  deletedAt       DateTime?

  roles           UserRole[]
  vendor          Vendor?

  @@index([status])
  @@map("users")
}

model Role {
  id          String   @id @default(uuid(7)) @db.Uuid
  name        String   @unique
  description String?
```

  express a cross-column FK consistency check like this; it stays an
  app-layer invariant.

  soft-deletable Catalog entities — this plan follows §53 as authoritative.
- `Inventory` has no `deletedAt`: `catalog.md` §53 says it "should remain
  available while historical business records reference the variant" —
  i.e., it lives and dies with `ProductVariant`'s own soft-delete state, not
  independently.
- `available = onHand - reserved` is **not** a stored column (per §32) —
  it must be computed in queries/service code.
- **Finalized (Final Decisions §9):** `Inventory.onHand >= 0`,
  `reserved >= 0`, and `reserved <= onHand` (§33) are adopted as DB-level
  `CHECK` constraints, added as a raw-SQL edit to the Phase 3 migration
  (Prisma's schema language has no native `@@check` attribute):

  ```sql
  ALTER TABLE "inventories"
    ADD CONSTRAINT "inventories_on_hand_non_negative" CHECK ("on_hand" >= 0),
    ADD CONSTRAINT "inventories_reserved_non_negative" CHECK ("reserved" >= 0),
    ADD CONSTRAINT "inventories_reserved_lte_on_hand" CHECK ("reserved" <= "on_hand");
  ```

  This is defense-in-depth alongside the app-layer transaction safety in
  §1.9, not a replacement for it — the transaction pattern is still what
  prevents lost updates under concurrency; the `CHECK` constraint is the
  last-line guarantee that no code path (including a future bug) ever
  commits an invalid row.

plain `CHECK`) to enforce at the DB level, which is out of scope here. They
remain enforced solely by the atomic transaction pattern in §1.9 (lock
wallet row → validate → update balance + insert `WalletTransaction`

# Part 6 — Migration Execution Plan

**Implementation Decision:** run one `prisma migrate dev` per phase, in the
Part 2 order, rather than one giant initial migration. This is a greenfield
database (no production data yet), so a single migration would also work,
but per-phase migrations give:

- a reviewable migration history that mirrors the domain docs 1:1,
- an easy point to stop and manually verify each domain (e.g., confirm the
  `Cart` partial unique index from §1.11 was generated correctly) before
  moving on,
- natural checkpoints for adding phase-specific seed data (roles in Phase 1,
  the identifier sequences in Phases 5–6).

```text
1.  Write prisma/schema/schema.prisma (generator + datasource only)
    → include previewFeatures = ["partialIndexes"] (§1.11) from the start,
      even though it's only exercised in Phase 4, so it doesn't get
      forgotten and force a regeneration later
2.  Write prisma/schema/enums.prisma                        (Part 4)
3.  Write prisma/schema/identity-access.prisma               (Part 5, Phase 1)
    → npx prisma migrate dev --name init_identity_access
    → seed ADMIN / VENDOR / CUSTOMER roles
4.  Write prisma/schema/vendor-shop.prisma                   (Phase 2)
    → npx prisma migrate dev --name init_vendor_shop
5.  Write prisma/schema/catalog.prisma                       (Phase 3)
    → npx prisma migrate dev --name init_catalog
6.  Write prisma/schema/cart.prisma                          (Phase 4)
    → npx prisma migrate dev --name init_cart
    → verify the generated migration.sql contains the partial
      `CREATE UNIQUE INDEX ... WHERE status = 'ACTIVE'` (native output of
      the `where: raw(...)` attribute — no manual SQL edit expected)
7.  Write prisma/schema/order.prisma                         (Phase 5)
    → npx prisma migrate dev --name init_order --create-only
      (drafts the migration without applying it — `prisma migrate dev`
      without `--create-only` both generates *and* applies in one step, so
      the draft-first form is required whenever the SQL needs a manual edit
      before it touches the database)
    → edit the generated migration.sql and add:
      CREATE SEQUENCE order_number_seq;
      (§1.10)
    → npx prisma migrate dev --name init_order
      (re-running without `--create-only` detects the existing draft
      migration and applies it as edited, instead of generating a new one)
8.  Write prisma/schema/payment-refund.prisma                (Phase 6)
    → npx prisma migrate dev --name init_payment_refund --create-only
    → edit the generated migration.sql and add:
      CREATE SEQUENCE payment_number_seq;
      CREATE SEQUENCE refund_number_seq;
    → npx prisma migrate dev --name init_payment_refund
      (applies the edited draft)
9.  Write prisma/schema/wallet-commission.prisma             (Phase 7)
    → npx prisma migrate dev --name init_wallet_commission
10. Write prisma/schema/promotion.prisma                     (Phase 8)
    → npx prisma migrate dev --name init_promotion
11. Write prisma/schema/review.prisma                        (Phase 9)
    → npx prisma migrate dev --name init_review
12. Write prisma/schema/notification.prisma                  (Phase 10)
    → npx prisma migrate dev --name init_notification
13. Write prisma/schema/audit.prisma                         (Phase 11)
    → npx prisma migrate dev --name init_audit
14. npx prisma generate                                      (regenerate client once, or after each phase)
15. Update prisma.config.ts: schema: 'prisma/schema' (directory form, §3)
```

Each step also requires updating the cross-file back-relation fields on
earlier models (e.g., adding `vendorOrders VendorOrder[]` to `Vendor` in
`vendor-shop.prisma` when Phase 5 is implemented) — Prisma requires both
sides of every relation to be declared somewhere in the merged schema.
This plan's per-entity snippets in Part 5 show the FK-owning side in full;
the corresponding list-field additions to earlier files are implied and
should be applied at each step, not deferred to the end.

## Final Decisions

Resolution for every question raised in Part 10, plus the two items this
review round was specifically asked to verify (partial indexes, UUID
version). All are final; implementation should proceed on this basis
without re-litigating them.

1. **UUID v4 vs v7 → UUID v7, platform-wide, no exceptions.**
   `@default(uuid(7))` on every model (updated across all 35 model
   snippets in Part 5). No architectural conflict exists — the source docs
   never pin a UUID version. Supported since Prisma ORM 5.18.0 (Aug 2024)
   with no preview-feature flag required; this repo is on `^7.9.1`. Chosen
   for B-tree insert locality on high-volume tables (`OrderItem`,
   `WalletTransaction`, `InventoryTransaction`, `AuditLog`, `Notification`,
   both status-history tables, `CouponRedemption`) and as a minor
   operational win (time-sortable IDs).

2. **Active-cart partial unique index → native Prisma schema syntax,
   not a manual migration edit.** Verified against the installed Prisma
   version: the `partialIndexes` preview feature (present since the 7.4
   line, confirmed current at `^7.9.1`) adds a `where: raw("...")` argument
   to `@@unique`/`@@index`/`@unique` for PostgreSQL. `Cart` now declares
   `@@unique([userId], map: "cart_one_active_per_user", where: raw("status
   = 'ACTIVE'"))` directly in `cart.prisma` (§1.11, Phase 4). Requires
   `previewFeatures = ["partialIndexes"]` in the generator block from the
   start (Part 3, Part 6 step 1). No hand-edited migration SQL is needed
   for this constraint.

3. **`Commission.vendorOrderId` stays `@unique` — confirmed correct.**
   It is the right encoding of the one-commission-per-VendorOrder model
   `wallet-commission.md` §28–33 and §43–44 already assume (corrections
   happen via a `status` transition on the same row, never a second row).
   No change from draft 1.

4. **Multi-file Prisma schema structure — kept.** One `.prisma` file per
   domain under `prisma/schema/`, mirroring `docs/database/*.md` 1:1
   (Part 3).

5. **Per-domain migration strategy — kept.** One `prisma migrate dev` per
   phase, in the Part 2 dependency order, rather than a single initial
   migration (Part 6).

6. **snake_case DB mapping via `@@map`/`@map` — adopted.** Prisma models
   and fields stay `camelCase`/`PascalCase`; Postgres tables and columns
   are `snake_case` (§1.7). Applied consistently across every model in
   Part 5.

7. **`Decimal(14, 2)` platform-wide monetary precision — adopted.**
   Applies to every money field across every domain except
   `Commission.rate`, which stays `Decimal(5, 2)` as a percentage (§1.4).

8. **Sequence-based `orderNumber` / `paymentNumber` / `refundNumber`
   generation — adopted.** Dedicated Postgres `SEQUENCE` per prefix
   (`order_number_seq`, `payment_number_seq`, `refund_number_seq`),
   `nextval()`-formatted at the application layer inside the creating
   transaction (§1.10). Chosen over ULIDs because it keeps the
   human-readable `PREFIX-YEAR-000001` format the source docs already
   specify, while still being collision-safe under concurrency.

9. **Optional DB-level `CHECK` constraints — adopted selectively.**
   Added, as raw-SQL migration edits (Prisma has no native `@@check`
   attribute, confirmed), for the cheap single-row invariants the source
   docs state as hard rules:
   - `Review.rating BETWEEN 1 AND 5` (`review.md` §5),
   - `Inventory.onHand >= 0`, `Inventory.reserved >= 0`, and
     `Inventory.reserved <= onHand` (`catalog.md` §33).

   **Not** added as `CHECK` constraints: `Wallet.balance =
   availableBalance + pendingBalance` and the related non-negativity rules
   (`wallet-commission.md` §26–27). These are cross-field, transaction-scoped
   invariants that would require a trigger (not a plain `CHECK`) to enforce
   at the DB level, which is beyond this plan's scope — they remain
   enforced by the atomic transaction pattern in §1.9 (lock wallet row,
   validate, update balance + insert `WalletTransaction` together).
